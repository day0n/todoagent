# Council

把本机已安装的编码 CLI（Claude Code、Codex、Cursor、Gemini、Kiro、Grok）组成一支有分工、会互相挑错的专家团队。你交代一个目标，它拆解、并行执行、交叉评审，最后交回一份被审查过的结果。

## 它和现有产品的区别

Multica 和 Raft 都做同一件事的组织层：本地 daemon 跑 agent、用你自己的订阅、云端只做看板。区别在**执行模型**：

| | Multica | Raft | Council |
|---|---|---|---|
| 主界面 | issue 列表 | 聊天频道 | 单个 run |
| 谁填看板 | 人和 agent | 你 | 编排者（你只给一句话）|
| 任务依赖 | stage barrier | 无（你手动把关）| stage barrier |
| Agent 互评 | 无 | 无（你自己看）| 交叉评审 + 复现验证 |
| 控制流 | 提示词里的协议 | 提示词里的协议 | **TypeScript 代码** |

最后一行是核心：编排逻辑是确定性代码，不是让 LLM 自己决定下一步。自由讨论的多 agent 不会收敛到真理，会收敛到**先发言的那个**——那正好销毁了付多家厂商钱买来的独立视角。

## 前提

至少装一个编码 CLI，并确认它已登录：

```bash
pnpm doctor --probe
```

`--probe` 会对每个 CLI 真跑一轮对话。这一步不能省：`detect` 只证明二进制存在，凭据过期的 CLI 看起来完全一样。本机实测结果：

```
claude   2.1.220        OK
codex    0.146.0        OK
cursor   2026.07.23     OK
kiro     2.12.2         OK
grok     0.2.117        OK
gemini   0.19.4         FAIL — 需要 GEMINI_API_KEY
```

## 启动

```bash
pnpm install
pnpm seed ~/你的仓库          # 按已装 CLI 自动组队
pnpm dev                      # 引擎 :8787
pnpm dev:web                  # 界面 :3000
```

目标仓库**必须是 git 仓库**。并行执行靠 worktree 隔离，没有它多个 agent 会互相覆盖文件。

## 六个阶段

```
拆解 → 并行执行 → 交叉评审 → 反驳 → 裁决 → 验证
```

- **拆解**：编排者读代码产出子任务 DAG，然后**停下来等你确认**。这是最便宜的介入点——30 秒检查拆解，能省掉后面几个 agent 做错方向和几轮评审的浪费。
- **并行执行**：同批子任务各自一个 git worktree，彼此看不见对方产出。后一批开始前，前一批先合并进来。
- **交叉评审**：每份产出被另外两位专家独立评审。评审者不能是作者。
- **反驳 / 裁决 / 验证**：作者逐条回应，编排者收口，最后跑构建和测试。

### 唯一重要的规则

> 能被客观验证的争议，交给测试；只有不可验证的争议，才值得占用你的注意力。

评审时每条意见都要标 `verifiable`：

- 「这里有竞态」→ 可验证 → 让提出者**写一个能复现的失败测试**。红灯说明问题真实，绿灯说明它判断错了。一个复现胜过三轮争论。
- 「这套灰阶层次乱」→ 不可验证 → 这才是摆到你面前让你拍板的东西。

被测试**否证**的意见立刻停止阻塞，不再消耗反驳、裁决、返工三轮。

## 人只在两处介入

**确认拆解方案**，和**裁决测试无法判定的分歧**。其余全自动。

## 边界

一律硬上限，没有「直到达成一致」这种不可判定的终止条件：

- 评审轮次 ≤ 2，讨论轮次 ≤ 2（或全员无话可说时提前收敛）
- 拆解上限 12 个子任务。一个子任务约等于 6 轮 agent（执行 + 2 个评审 + 复现 + 反驳 + 裁决），所以 50 个子任务是 300 轮——预算闸门能拦住，但要等钱烧完才拦。真需要更多就拆成多次委托。
- Token 预算是硬上限，超出即停并交出中间产物
- 并发 agent 进程默认 `min(核数/2, 6)`，可用 `COUNCIL_MAX_CONCURRENT_AGENTS` 调整。这是**全局**上限：子任务并行和评审者并行是嵌套的，各自限流会让峰值变成两者相乘（6 个子任务 × 2 个评审 = 12 个完整 CLI 进程，每个几百 MB 还会自己拉起构建工具）。所以是一个信号量守住唯一的进程创建点。
- 三层看门狗：通用静默、工具执行中（更长预算）、墙钟上限。杀进程时信号整个进程组——只杀直接子进程会留下孙进程握着 stdout 管道，`close` 永不触发。
- **一个仓库同时只跑一个委托**。两个委托会往同一个工作分支并发 merge，git 会把结果搅坏且不可撤销；让你等一下的代价小得多。

## 不会静默失败的地方

这些都是实测发现并修掉的，列出来是因为它们的失败形态都是「看起来成功了」：

- 取消之后不会再合并任何东西，状态也不会被改写成「已完成」
- 已取消/已完成的委托无法被「恢复」，而且拒绝是同步的 HTTP 错误，不是先回 ok 再在后台失败
- 返工时作者会收到评审原话、自己上一轮的反驳、以及裁决理由（返工不共享会话，不重述等于让它凭空重做）
- 你的裁决会真正回到 agent 手里并让它重跑，而不是只写进数据库
- 合并冲突和未通过评审的产出只上报、不自动处理，分支保留
- 建项目时就校验是不是 git 仓库，而不是等到跑委托才失败

## 命令

```bash
pnpm doctor --probe     # 实测每个 CLI 能否完成一轮
pnpm test               # 244 个测试（core 206 + engine 25 + web 13）
pnpm typecheck

```

## 架构

```
apps/web      Next.js 界面（run 为中心，不是待办看板）
apps/engine   Hono + SSE，仅监听 127.0.0.1
packages/core 适配器、编排器、SQLite
```

三种传输格式被适配器统一成同一个事件流：stream-json（claude/cursor/gemini）、JSONL（codex）、ACP over JSON-RPC（kiro/grok）。这个抽象照抄 Multica 的 `Backend`/`Session`——它已经被 18 个后端验证过。

## 安全

**仅 localhost，且故意不做认证。** 所有适配器都以绕过工具确认的方式运行 CLI（`--permission-bypassPermissions`、`--yolo`、`--always-approve`）。单人本机工具可以接受；**一旦暴露端口，任何能访问的人都能在你机器上以你的凭据执行任意代码**。对外提供服务前必须先加认证和沙箱。

## 已知限制

- **客户端水合未验证**：页面 SSR 不崩、API 数据正确都已实测，但渲染后的 DOM 需要真实浏览器才能验证。
- **gemini 适配器未经真实运行**：本机缺 API key，它的解析代码从未被执行过，事件名属推测（参照 Qwen Code——它是 Gemini CLI 的 fork）。
- **「谁擅长什么」是社区经验，不是测量结果**，而且每次模型更新都会漂移。所以它是 `experts.capabilities` 里的数据而非写死的逻辑。每个 run 都记录了谁做的、评审结论、是否被采纳——跑够二十次就能用真实数据校准路由表。
- 合并冲突只上报，绝不自动解决。机器随手挑一边正是这套系统要避免的静默损坏。
- **事件日志不做清理，这是量过之后的决定**：一次长委托约 2.7 MB（2880 个事件），50 次约 130 MB。单人本机工具按每天几次算，一年才到 GB 量级——为此引入保留策略和 TTL 清理，比问题本身更麻烦。Multica 需要 GC 是因为它是多工作区的常驻守护进程，前提不同。
- 工作区有未提交改动时会拒绝启动（单专家模式除外）。worktree 从 HEAD 切出，agent 看不见你正在改的代码，而且 git 会在最后一步拒绝合并——那时钱已经花完了。
